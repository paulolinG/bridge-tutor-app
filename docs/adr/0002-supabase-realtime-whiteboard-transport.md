# The shared whiteboard syncs over Supabase Realtime, not a tldraw sync server

Embedding tldraw is easy; making it multiplayer is a separate piece of infrastructure the library does not ship. tldraw's own sync is a websocket server you host, and Excalidraw's collaboration runs through Excalidraw's server — neither is free-by-default for us. Hosting a sync server on Render's free tier is the option that looks obvious and fails quietly: that tier sleeps after fifteen minutes idle, which is fatal to long-lived websockets, so the whiteboard would die exactly when a session runs long or starts late.

So live document deltas are broadcast over Supabase Realtime channels instead, keyed by session. Supabase is already provisioned, the free tier covers pilot volume comfortably (200 concurrent connections, 2M messages/month), and it needs no new service, no new bill, and no new thing that can be asleep. The same channel then carries the rest of the session's ephemeral state — the tutor-to-student page flip when a session ends, and announcements of AI-rendered images available to insert — so there is one live transport rather than three.

The cost is a stated exception to "the frontend never queries Supabase directly." That rule exists so application data has exactly one gateway (FastAPI) and the anon key is never a data-access path. Realtime broadcast doesn't breach that: it carries ephemeral messages between two clients and reads no tables. Anything durable — `session_messages`, diagnostics, error flags — is still written through FastAPI. The rejected alternative worth naming is a tutor-only board shared via Daily's screen share, which needs no sync at all and ships in a day; it was turned down because it removes the student's ability to draw, and a student working a problem where their tutor can watch is most of the point of a shared workspace.
