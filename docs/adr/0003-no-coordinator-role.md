# There is no coordinator role, and no admin dashboard

The specification referred to an admin or coordinator in six places — an admin dashboard showing expired requests, admin-visible tutor quality scores, admin-entered region multipliers, admin-entered session requests, and an admin-mediated notification policy — while simultaneously specifying that tutors are the only accounts in the product. Nothing reconciled the two, and no admin surface was ever built.

We resolved it toward the second statement: a coordinator is a human with direct database access, not a role in the system. There is no admin login, no `role` column, no admin-gated dependency, and no admin UI. Coordinators enter session requests and regions through the Supabase table editor. A future reader will reasonably wonder why the docs talk about a dashboard that does not exist, hence this record.

The alternative was building the role for real, and the cost is out of proportion to the user: a role column, admin-gated route dependencies, an invite flow, and an entire second UI surface — serving one person who already holds the service-role key and can edit any row directly. The tempting half-measure, a tutor-authenticated page that happens to list all requests, is worse: it is the same admin surface with weaker access control, since every certified tutor could then read every student's request.

The one thing this genuinely broke was notification. The old policy read "the coordinator sees it on the dashboard and reaches out to the student," which no longer describes anything. Each batch run that changed something now emails a single coordinator address a digest of new matches and expirations, and a run that changed nothing sends nothing — which is most runs. Without that, a 3am batch run would match a request and tell no one, leaving a student with a join link they never receive. Revisit all of this when a second person needs the coordinator job; at that point it is a real feature, not a footnote.
